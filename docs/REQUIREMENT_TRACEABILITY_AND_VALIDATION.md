# Requirement Traceability and Validation —
This matrix is based on the supplied **Technical Assessment — AI Document Investigation Agent** document. It maps the stated requirements to the current implementation and tests that should be executed. A mapped test is not evidence of a pass until the test has actually run.
| Assessment requirement | Current implementation | Validation approach | Known caveat / evidence to collect |
|---|---|---|---|
| Investigate a user question across multiple documents | Owner-scoped document chunks are searched and relevant excerpts are passed to Mock AI or Ollama | Upload two documents containing complementary facts; ask a question that needs both; inspect returned source passages | Keyword search may miss semantically related passages; record the exact source text and response |
| Identify relevant information and gather supporting evidence | Keyword evidence retrieval returns document/chunk references, offsets, excerpts, matched terms, and ranking score | Search for an exact phrase and a paraphrased query; verify filenames, chunk indices, excerpts and offsets | Ranking score is not a probability; paraphrase retrieval can be weak |
| Compare information across documents | Retrieved passages are available to the investigation workflow; Mock AI includes deterministic conflict handling for opposite statements | Upload two policies with conflicting values; ask the same question; verify conflict status and evidence references | Real LLM behavior is probabilistic; repeat with Ollama and manually inspect all statements |
| Decide whether information is sufficient | Investigation statuses include insufficient evidence and clarification required | Ask a supported question, an unrelated question, and an ambiguous question | Verify status and message rather than expecting a specific wording from the real LLM |
| Communicate ambiguity or request clarification | Clarification status and clarification question are part of the response; a status-based `recommendedNextAction` is included | Ask a vague question such as “What about it?” and inspect response | Real LLM may not consistently classify ambiguity; record actual output |
| Final answer includes a clear conclusion | `InvestigationResponse.conclusion` is rendered as Conclusion in the UI | Ask a question whose answer is explicitly in the uploaded file | Confirm response is understandable and matches the source |
| Final answer includes supporting evidence and document references | Evidence references include source filename/document ID/chunk index/quote | Verify each displayed citation points to a returned retrieved chunk and source excerpt | Citation-ID validation does not prove semantic entailment of every answer sentence |
| Final answer identifies conflicts or missing information | Status values include `CONFLICTING_EVIDENCE`, `INSUFFICIENT_EVIDENCE`, and `CLARIFICATION_REQUIRED` | Test conflicting, absent, and ambiguous information cases | A dedicated “missing information” narrative may vary by status/provider |
| Final answer recommends a next action where applicable | Response includes a status-based `recommendedNextAction` and UI section | Test insufficient and ambiguous cases and verify a clear next step is shown or inferable | Status-based action text is provided; verify that it is appropriate for each result status |
| Invalid inputs are handled | Jakarta validation and structured exception handling cover invalid question, limits, JSON, headers, IDs, and upload errors | Execute negative API and UI cases; confirm controlled 4xx response and no stack trace | Verify exact status and message from actual run |
| AI or processing failures are handled | Provider failure is caught and response/audit failure path exists | Stop Ollama after app startup and run an investigation in Ollama mode | Confirm safe failure status, no provider stack trace or secrets; ensure the audit record is written |
| Unauthorized document access is handled | Data access is scoped by `X-User-Id`; cross-owner reads should not reveal records | Create data as `demo-user`; attempt reads/search as `user-two` | `X-User-Id` is a demo identity header, **not real authentication**; production auth is not implemented |
| Situations that cannot be completed safely | Prompt-injection guardrails treat retrieved text as untrusted; citations are checked against retrieved IDs | Upload a document containing “ignore previous instructions”; ask an evidence question | Manual adversarial testing is required; guardrails reduce but do not eliminate risk |
| Activity is traceable and reviewable | Audit events and persisted investigation/evidence records | Upload, search, investigate; inspect H2 tables and verify actor/resource/action/time are recorded | Avoid storing unnecessary sensitive text; validate audit details against schema |
| Java 17 or later | Project uses Java 21 in `pom.xml` | `java -version`, then `mvn clean test` | JDK 21 is recommended for this project configuration |
| Spring Boot and REST APIs | Spring Boot controllers expose document, search and investigation endpoints | Open Swagger and run positive/negative endpoint cases | UI calls the same REST APIs |
| Persistence | File-based H2 at `./data/document-agent`; test profile uses in-memory H2 | Save records, restart normally, fetch records again | Keep the working directory stable so the relative database path resolves consistently |
| LLM or mock LLM | Mock provider plus Spring AI Ollama provider | Run automated tests in Mock mode; run manual Ollama scenarios separately | Automated tests do not establish live LLM answer quality |
| README covers run steps, assumptions, design decisions, limitations and AI tools | README and `docs/` cover these areas | Review README and linked design/testing docs before submission | Update docs if implementation changes |
| Assessment time limit: two calendar days / 8–10 hours | Scope kept to a modular monolith, keyword retrieval, H2, Thymeleaf and local LLM option | Keep a final scope review; prioritize required behaviors over new infrastructure | Do not add vector DB, microservices, or a separate frontend unless justified by assessment needs |
## Validation exit criteria
1. `mvn clean test` completes with `BUILD SUCCESS`, zero failures, and zero errors.
2. Manual tracker cases have actual outcomes recorded; none are marked Passed without execution.
3. Positive scenarios produce expected records and evidence; negative scenarios fail safely.
4. Owner-isolation tests demonstrate no cross-user data leakage under the demo identity model.
5. Ollama is tested separately from Mock AI, including an unavailable-provider scenario.
6. Known limitations are disclosed in README and during the assessment walkthrough.
